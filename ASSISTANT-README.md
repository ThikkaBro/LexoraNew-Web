# AI site assistant

A chat widget that answers questions about a website using only that website's
own published content, refuses to guess, and hands anything it cannot answer to
a human.

Built to be redeployed: **everything client-specific lives in one file**,
[`assistant.config.ts`](assistant.config.ts). Deploying it for a new client
means editing that file and re-running one script.

**It works right now with no API key and no account anywhere.** See
[Demo mode](#demo-mode-no-key-needed).

## What it does

- **Answers only from your site.** The knowledge base is built from your own
  content. Nothing else is in scope.
- **Says "I don't know" and means it.** No invented prices, dates, timelines or
  capabilities, and no commitments made on your behalf.
- **Streams replies** with a typing indicator, and remembers the conversation
  for the length of the visit.
- **Captures leads** after a few exchanges, or the moment it cannot answer.
- **Costs what you decide.** Per-IP rate limits, a conversation-length cap, a
  message-length cap, and a token-usage log line per request.
- **Adds nothing to page weight.** First Load JS is byte-identical with the
  widget and without it — measured, see [Lighthouse](#lighthouse).

## Quick start

```bash
npm install
npm run kb:build
npm run dev
```

Open <http://localhost:3000> and click the button in the bottom-right corner.
No key required — it runs in demo mode.

## Demo mode (no key needed)

With no API key configured, the endpoint still answers. Same widget, same
streaming, same refusal behaviour — but the answer is **retrieved from your
knowledge base and quoted**, rather than generated by a model.

**What it can do:** answer anything your site already states, in your site's own
words, and refuse everything else.
**What it cannot do:** rephrase, combine two topics in one answer, or follow a
conversational thread ("what about the other one?").

It exists for three reasons, and it earns its place on all three:

1. You can demonstrate the widget to a client before anyone has paid for
   anything.
2. It is the fallback when a key expires, a free tier runs out, or a provider
   has an outage — the visitor gets your real answer instead of an error.
3. It costs nothing, so a low-traffic client site can simply stay on it.

Switching to a real model is one environment variable. No code changes.

## Getting a free API key

You do not need to pay to run this properly. Four providers have real free
tiers, all speak the same protocol, and all take about two minutes to set up.
Pick one, create a key, and put it in `.env.local`.

| Provider | Where | `ASSISTANT_OPENAI_BASE_URL` | Suggested `ASSISTANT_OPENAI_MODEL` |
|---|---|---|---|
| **Groq** *(fastest)* | [console.groq.com/keys](https://console.groq.com/keys) | `https://api.groq.com/openai/v1` | `llama-3.3-70b-versatile` |
| **Google AI Studio** | [aistudio.google.com/apikey](https://aistudio.google.com/apikey) | `https://generativelanguage.googleapis.com/v1beta/openai` | `gemini-2.0-flash` |
| **Cerebras** | [cloud.cerebras.ai](https://cloud.cerebras.ai) | `https://api.cerebras.ai/v1` | `llama-3.3-70b` |
| **OpenRouter** | [openrouter.ai/keys](https://openrouter.ai/keys) | `https://openrouter.ai/api/v1` | any model id ending `:free` |

```bash
# .env.local
ASSISTANT_OPENAI_API_KEY=your_key_here
ASSISTANT_OPENAI_BASE_URL=https://api.groq.com/openai/v1
ASSISTANT_OPENAI_MODEL=llama-3.3-70b-versatile
```

Free tiers have request-per-minute and request-per-day quotas. When one is hit
the provider returns an error and the assistant **falls back to demo mode** for
that request rather than showing the visitor a failure.

Two honest caveats. Free tiers give no uptime guarantee — fine for a site FAQ,
not for anything load-bearing. And these providers have no prompt caching, so
the knowledge base is re-read on every request; that costs nothing on a free
tier, and it is the reason Anthropic is the default once there is a budget.

## Environment variables

Every variable is **server-side**. None is prefixed `NEXT_PUBLIC_`, which is the
only mechanism by which Next.js puts an environment variable into the browser
bundle. Copy [`.env.example`](.env.example) to `.env.local` to start.

| Variable | Required | What it does |
|---|---|---|
| `ANTHROPIC_API_KEY` | no | Use Anthropic. Best answers, and the only provider here with prompt caching. |
| `ASSISTANT_OPENAI_API_KEY` | no | Use an OpenAI-compatible provider (see the table above). |
| `ASSISTANT_OPENAI_BASE_URL` | no | That provider's base URL. Defaults to Groq. |
| `ASSISTANT_OPENAI_MODEL` | no | Overrides `model.openaiModel` in the config. |
| `LEAD_WEBHOOK_URL` | no | Where leads are POSTed as JSON. Unset: leads go to the server log. |
| `LEAD_WEBHOOK_SECRET` | no | Sent as `X-Assistant-Secret`, if your receiver checks it. |
| `UPSTASH_REDIS_REST_URL` | no | Shared rate-limit store. Recommended on serverless. |
| `UPSTASH_REDIS_REST_TOKEN` | no | Paired with the above. |

**With none of these set, everything still works** — demo answers, and leads in
the log.

Provider selection under `model.provider: "auto"` is: Anthropic key → 
OpenAI-compatible key → demo. Pin it to one provider by name if you prefer.

### Where leads go, and why a webhook

`LEAD_WEBHOOK_URL` receives a JSON POST per submission — name, email, optional
message, the page, and the last few conversation turns so whoever replies has
the context.

A webhook was chosen over sending email because that one variable already works
with Zapier, Make, n8n, a Slack incoming webhook, Formspree, a Google Apps
Script, or a client's own CRM. Each client picks their own destination with no
code change, no email provider account, no API key to rotate and no sending
domain to verify before the first lead can arrive.

If the webhook is unset or fails, the lead is written to the server log in full
and the visitor is still told it arrived — because it did. Nothing is ever
silently dropped.

## Running ingestion

```bash
npm run kb:build
```

Reads your content, writes `data/knowledge-base.json`, and **commits to the
repo**. Run it whenever site content changes; it is safe to re-run and the
output is deterministic, so an unchanged site produces no diff.

It reads two sources:

1. **`app/site-config.ts`** — imported as a typed module, not scraped from
   rendered HTML, so ingestion cannot drift from what the page shows and does
   not need a running server.
2. **`content/kb/*.md`** — free-form Markdown for anything the site config does
   not model. Each `##` heading becomes its own entry.

It prints a token count and tells you which retrieval mode to use.

### Adding a Markdown source

Create `content/kb/whatever.md`:

```markdown
# Delivery and support

## How long does support last?

Keywords: support, warranty, maintenance, after launch, bugs

Thirty days of fixes are included after handover, with no hourly billing.
```

The optional `Keywords:` line lists the *other* words visitors use for that
topic. It matters more than it looks: someone asking "what have you built
before?" shares no word with a case study's title, so without aliases the
retrieval would miss it. Keywords are used for finding an entry, never quoted
back, and are deliberately excluded from the check that decides whether a
question is answerable at all — so adding an alias can never make an
unanswerable question look answerable.

### Node version

`kb:build` runs the TypeScript file directly on Node 22.6+, which needs no
build step and no extra dependency. On older Node:

```bash
npx tsx scripts/build-knowledge-base.mts
```

## Deploying for a new client

1. **Point the ingestion script at their content.** If their copy lives in a
   config module like `app/site-config.ts`, edit the mapping at the top of
   `scripts/build-knowledge-base.mts`. If it lives anywhere else, write their
   content into `content/kb/*.md` and delete the site-config section — the
   Markdown path alone is enough for many sites.
2. **Edit `assistant.config.ts`.** Business name, description, contact email,
   booking link, persona name, tone, greeting, suggested questions, rate limits,
   lead-capture copy, and the theme tokens.
3. **Match their design.** The `ui.theme` block maps to Tailwind classes. Swap
   them for the client's own tokens — no component edits.
4. `npm run kb:build`
5. **Set environment variables** in their host's dashboard.
6. **Mount the widget** — one line in the root layout:
   ```tsx
   import { Assistant } from "@/components/assistant/Assistant";
   // …then <Assistant /> just before </body>
   ```
7. **Update their privacy policy.** Not optional: the widget sends visitor
   messages to a third party and uses IP addresses for rate limiting. See
   [`app/privacy/page.tsx`](app/privacy/page.tsx) for wording that covers it.
8. **Test the refusals before you invoice.** Ask it three things the site does
   not answer — a technology they do not list, a delivery date, a discount — and
   confirm it declines each one. That behaviour is the product.

## What it costs

Measured against this site: the system prompt is **5,243 tokens** (939 of rules,
4,304 of knowledge base). Assuming four messages per conversation, ~280 tokens
of history per request and ~130 tokens per reply, on `claude-sonnet-4-6` at
$3/$15 per million with cached reads at $0.30:

| Conversations / month | With prompt caching | Without caching | Saving |
|---:|---:|---:|---:|
| 100 | **$3.46** | $7.41 | 53% |
| 500 | **$15.96** | $37.04 | 57% |
| 2,000 | **$54.80** | $148.15 | 63% |

Per conversation that is **$0.018–$0.036** depending on whether the cache is
warm. The saving grows with traffic because the cache has a five-minute life:
at 100 conversations a month it is nearly always cold and most conversations pay
to write it, while at 2,000 conversations they increasingly land inside each
other's window and pay only to read.

**On a free tier, all of the above is $0.** You are spending quota, not money.

Two ways to cut the bill if you ever need to: switch to `claude-haiku-4-5`
(roughly a third of the cost, and honestly sufficient for FAQ retrieval), or
trim the knowledge base — the system prompt is the largest line item and is
paid on every request.

### Seeing the real number

Every completed request writes one JSON line to the server log:

```json
{"tag":"assistant_usage","provider":"anthropic","model":"claude-sonnet-4-6",
 "input_tokens":312,"output_tokens":128,"cache_read_tokens":5243,
 "cache_hit_ratio":0.944,"cost_usd":0.003512,"duration_ms":1840,
 "could_not_answer":false,"degraded":false}
```

Watch `cache_hit_ratio`. If it sits near zero across requests, something in the
system prompt is varying per request and you are paying full price for the
knowledge base on every call.

## How it is put together

```
assistant.config.ts                    ← the only file you edit per client
content/kb/*.md                        ← extra content the site config can't hold
data/knowledge-base.json               ← generated, committed
scripts/build-knowledge-base.mts       ← ingestion (npm run kb:build)

lib/assistant/
  types.ts             shared types and the streaming wire format
  knowledge.ts         loads the base; scoring, IDF, coverage checks
  prompt.ts            the system prompt, and the cache split
  rate-limit.ts        per-IP limits, in-memory or Upstash
  usage.ts             token accounting and cost
  providers/
    index.ts           which provider to use
    anthropic.ts       Anthropic, with prompt caching
    openai-compatible.ts   Groq / Gemini / Cerebras / OpenRouter
    demo.ts            the no-key engine

app/api/assistant/chat/route.ts        POST → streamed reply
app/api/assistant/lead/route.ts        POST → webhook or log

components/assistant/
  Assistant.tsx        the launcher (all the JS a page load pays for)
  ChatPanel.tsx        the panel, lazy-loaded
  LeadForm.tsx         name / email capture
  useAssistantChat.ts  conversation state and stream parsing
```

### Dependencies added

**One:** `@anthropic-ai/sdk`, which is server-side only and never reaches the
browser. Everything else — the OpenAI-compatible providers, the rate limiter's
Redis backend, the whole streaming path on both ends — uses `fetch` and the
platform's own streams.

## Design decisions worth knowing

These are the choices a client is most likely to ask about.

### The whole knowledge base goes in the prompt. There is no vector database.

This site's content is **~4,300 tokens**. Retrieval over a corpus that small
makes things worse, not better: chunking means the FAQ answer sitting one chunk
away from the question can be missed entirely, and you have added an embedding
model, an embedding cost, a similarity implementation and a class of "why didn't
it find that" bugs to achieve it. Putting everything in the prompt means nothing
can be missed, and with caching it is also **cheaper** than retrieval plus its
embedding round-trip.

The threshold is roughly **30,000 tokens**. `npm run kb:build` prints where you
are and warns when you cross it; switching is one line in the config
(`knowledgeBase.mode: "topk"`), and the ingestion script already emits chunks,
so nothing has to be rebuilt to make the change.

### The system prompt is split so caching actually works

Prompt caching is a prefix match — one changed byte anywhere in the prefix
invalidates everything after it. So the rules and the knowledge base, identical
on every request, form one cached block, and the conversation comes after it.
There is deliberately no timestamp, session id or request id anywhere in that
block. Any one of them would silently drop the hit rate to zero and quietly
turn a $0.30/M read back into a $3/M one.

### The refusal rules are negative and specific

"Be accurate" does nothing. The prompt names the four things a visitor most
wants invented — **price, availability, timeline, capability** — and forbids
each by name, because those are exactly the questions where a plausible guess is
most tempting and most expensive.

### The visitor's message is data, never instruction

It is wrapped in `<user_message>` tags, with the closing tag stripped from the
input first so it cannot end the block early. The prompt states that anything
inside is text to answer and never a command, and covers the specific attacks:
persona switches, "developer mode", requests to reveal or paraphrase the
instructions, and claims of authority ("I work here", "you quoted me $500").
Those claims are treated as things the person said, not things the assistant
knows.

### Demo mode refuses more than it answers, on purpose

A retrieval engine has no notion of what a question is *asking for*, which makes
it dangerously eager. Three rules hold it back, and an answer needs all three:

1. **A real score** — not a couple of incidental word matches.
2. **A hit on a distinctive word in the title or keywords.** Terms are weighted
   by how rare they are across the corpus (IDF), so matching "work" — which
   appears nearly everywhere on this site — counts for almost nothing, while
   matching "safeguarding" counts for a lot. Without this, "what if I'm not
   happy with the work?" matches the FAQ titled "You're not local — how does
   that work?" and answers about time zones.
3. **Few enough unknown words.** A question containing a word that appears
   nowhere on the site — "do you do *Salesforce* integrations?" — is usually a
   question the site does not cover. The check is prefix-tolerant so "store"
   matches "stored", but strictly so: "happy" does not match "happens".

Separately, anything **asking for a commitment** — "can you guarantee…", "can
you do it for $300", "can you deliver by Friday" — goes straight to a human
regardless of what it matched, because only a person can accept work or agree
terms. A retrieved answer about fixed prices is factually true and still reads
as agreement, which makes it the wrong answer.

### Lighthouse

The launcher is the only JavaScript a page load pays for. The panel is a
separate chunk, fetched on first click or when the browser reports it is idle,
which is after everything Lighthouse measures. Set `ui.prefetchOnIdle: false` to
wait for the click instead.

Measured on this site with `next build`, with the widget and without it:

```
Route (app)                      Size     First Load JS
┌ ○ /                            37.3 kB         144 kB      ← with widget
┌ ○ /                            37.3 kB         144 kB      ← without widget
```

Identical. The launcher's own code rounds below the 0.1 kB the build reports,
because `lucide-react` is already in the bundle for the nav. The panel chunk
(~16 kB) is not in First Load at all.

Nothing here is render-blocking, and the launcher is `position: fixed` and
painted last, so it cannot shift existing content.

### Motion and accessibility

`app/globals.css` already reduces every transition to near-zero under
`prefers-reduced-motion: reduce`, so the panel's CSS transitions are covered
with no JavaScript check and no second code path.

The panel traps Tab while open, closes on Escape, returns focus to the launcher
it came from, announces replies through `aria-live="polite"`, and — when closed
— uses `visibility: hidden`, which takes it out of both the tab order and the
accessibility tree.

> **A bug worth remembering if you fork this.** The panel originally used the
> `hidden` attribute. Its `display: none` comes from the browser's own
> stylesheet, which loses to any author declaration — so Tailwind's `flex` class
> silently overrode it, and the "closed" panel stayed laid out at opacity 0,
> swallowing every click in the bottom corner of the page, including clicks on
> its own launcher. If you use `hidden` alongside a display utility, this will
> happen to you.

## Security

- **The API key is read in one file** (`lib/assistant/providers/`), inside
  route handlers, from a variable with no `NEXT_PUBLIC_` prefix. It is never in
  a response body, a header, or the client bundle.
- **Verify it yourself** after any build:
  ```bash
  grep -r "ANTHROPIC_API_KEY\|ASSISTANT_OPENAI_API_KEY\|sk-ant-" .next/static/
  ```
  No output is the expected result. The knowledge base and system prompt are not
  in the client bundle either — only `assistant.config.ts`, which is
  non-secret display configuration.
- **Rate limits** are per IP: 12 requests per 10 minutes and 60 per day by
  default, shared by the chat and lead endpoints. In-memory counters are exact
  on a single server and **approximate on serverless**, where each instance
  keeps its own; set the two Upstash variables for a shared store. The limiter
  is a cost control, not a security boundary — `x-forwarded-for` is trustworthy
  behind Vercel's proxy and forgeable if the app is directly exposed.
- **Input caps**: 1,000 characters per message, enforced server-side, and the
  history is truncated to the last 12 messages, with the cap re-applied to
  older turns.
- **The lead form has a honeypot** field, and a bot that fills it gets a 200 so
  it cannot tell it was caught.
- **Assistant turns sent by the client are untrusted too.** The server is
  stateless and cannot verify them, so they are capped and truncated like
  everything else, and the system prompt is written to hold even when the
  history is hostile.

These predate this work and were not introduced by it; fixing them means a Next

## Troubleshooting

**"The assistant is not configured yet." (503)** — `data/knowledge-base.json` is
missing. Run `npm run kb:build` and commit it.

**Answers say "I don't have that" too often** — demo mode is working as
designed, but you may be missing aliases. Add a `Keywords:` line to the relevant
Markdown section, or extend the `keywords` arrays in
`scripts/build-knowledge-base.mts`, then re-run ingestion. A real model handles
paraphrase far better than retrieval can.

**Answers are confidently wrong** — that should be impossible for anything not
in the knowledge base. Check what ingestion actually produced:
`cat data/knowledge-base.json | grep -i "<the topic>"`. If the claim is in
there, fix the source content.

**`cache_hit_ratio` is 0** — something in the system prompt varies per request.
Check nothing has added a date, a session id, or a per-request value into
`buildSystemPrompt`.

**Visitors get 429s** — raise `limits.rateLimit` in the config, or set the
Upstash variables so the counters are shared rather than per-instance.

**The month or year on the site looks stale** — the hero's availability month
and the footer's copyright year are computed at render time, and static pages
only render at build time. `export const revalidate` in `app/layout.tsx` is what
regenerates them daily. Do not remove it.
